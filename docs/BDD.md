# 行為驅動開發規範 (Behavior-Driven Development, BDD)

本文件定義 ASR 轉寫後透過 LLM (`192.168.1.100:8002/v1`) 進行錯別字語意校正、四大區塊結構化會議紀錄整理，以及透過獨立腳本（Script）執行轉會議紀錄的驗收測試場景。

---

## 核心業務邏輯測試場景 (Happy Path)

### 功能 1：ASR 逐字稿語意錯別字校正
```gherkin
功能: ASR 轉錄後語意錯別字校正
  作為 一名會議紀錄使用者
  我希望 系統在 ASR 轉錄出原始逐字稿後，自動發送至 LLM (192.168.1.100:8002/v1) 修正同音錯別字與專有名詞
  以獲得 高品質且通順的校正逐字稿

  場景: 成功校正 ASR 轉錄稿中的錯別字
    假設 語音轉寫服務已完成音檔轉寫，產生原始逐字稿:
      "[00:00:05] 講者 A: 我們今天要討論 Breeze ASR 與 Ollama 模形整合。"
    當 系統發送校正請求至 "http://192.168.1.100:8002/v1/chat/completions"
  場景 1.2: 透過 /v1/models 動態查詢伺服器運行之模型名稱
    假設 伺服器 "http://192.168.1.100:8002/v1/models" 運行的模型清單包含 "nvidia/Qwen3.6-35B-A3B-NVFP4"
    當 系統初始化 LLMClient 或未指定模型名稱時
    則 系統應自動發送 GET 請求至 "/v1/models"
    並且 解析出當前可用的第一個模型 ID 作為後續請求之 model 參數
    並且 若伺服器查詢失敗則優雅回退至設定檔之備援模型名稱
```

### 功能 2：整理包含四大重點之會議紀錄
```gherkin
功能: 整理包含四大重點之會議紀錄
  作為 一名團隊主管
  我希望 LLM 生成的會議紀錄嚴格包含「會議重點」、「關鍵決策」、「TODO / 行動項目」與「下次會議追蹤項目」
  以便於 快速追蹤專案進度與會議產出

  場景: 根據校正後逐字稿生成符合四區塊結構之會議紀錄
    假設 已取得校正後之逐字稿
    當 系統發送會議紀錄提示詞至 "http://192.168.1.100:8002/v1/chat/completions"
    則 生成之會議紀錄 Markdown 內容必須包含以下區塊：
      - "# 會議名稱："
      - "## 【會議重點】"
      - "## 【關鍵決策】"
      - "## 【TODO / 行動項目】"
      - "## 【下次會議追蹤項目】"
    並且 TODO / 行動項目中需標明負責人與預計完成日期（若逐字稿中有提及）
```

### 功能 3：使用獨立 Script 執行轉會議紀錄
```gherkin
功能: 透過獨立腳本 (Script) 一鍵轉出會議紀錄
  作為 終端機使用者
  我希望 能夠直接在命令列執行 Python 腳本，傳入音訊檔案或現有逐字稿，自動完成錯別字校正與會議紀錄生成並存檔
  以便於 自動化批次處理與命令列工作流程

  場景 3.1: 傳入音訊檔案執行完整 pipeline
    假設 終端機存在音訊檔案 "meeting.mp3"
    當 使用者執行 "python scripts/transcribe_and_summarize.py --audio meeting.mp3"
    則 系統應先呼叫 ASR 轉出逐字稿
    並且 呼叫 LLM 進行語意錯別字校正
    並且 呼叫 LLM 生成四大區塊會議紀錄
    並且 自動於 "output/YYYY-MM-DD/" 匯出 "[會議名稱]_逐字稿.md" 與 "[會議名稱]_會議紀錄與摘要.md"
    並且 命令列顯示執行成功訊息與檔案存檔路徑

  場景 3.2: 傳入現有逐字稿檔案跳過 ASR 直接轉會議紀錄
    假設 終端機存在文字檔案 "transcript.txt"
    當 使用者執行 "python scripts/transcribe_and_summarize.py --transcript transcript.txt"
    則 系統應略過 ASR 轉寫步驟
    並且 呼叫 LLM 進行語意錯別字校正
    並且 呼叫 LLM 生成四大區塊會議紀錄
    並且 自動於 "output/YYYY-MM-DD/" 匯出對應 .md 檔案
```

## 異常與邊界條件場景 (Edge Cases & Unhappy Path)

### 場景 4：LLM 服務連線失敗時之降級處理 (Unhappy Path)
```gherkin
  場景: 192.168.1.100:8002 服務未啟動或連線超時
    假設 LLM 伺服器 "http://192.168.1.100:8002/v1" 連線失敗或回應超時 (Timeout)
    當 系統執行錯別字校正與會議紀錄生成
    則 系統應擷取連線例外狀況並輸出 Warning Log
    並且 校正逐字稿應自動降級回退為原始 ASR 逐字稿內容
    並且 會議紀錄摘要應顯示「摘要生成失敗：無法連線至 LLM 服務」
    並且 腳本不應崩潰 (Crash)，且 exit code 應有適當提示
```

### 場景 5：LLM 輸出包含 `<think>` 思考標籤之格式過濾 (Edge Case)
```gherkin
  場景: 思考型 LLM 模型將推理過程包裹於 <think> 標籤中
    假設 LLM 響應內容包含 "<think>正在分析上下文...</think># 會議名稱：技術分享會\n\n## 【會議重點】\n..."
    當 系統解析 LLM 回應結果
    則 系統應自動過濾並移除 "<think>...</think>" 區塊
    並且 最終輸出中僅保存乾淨的 Markdown 內容
```

### 場景 6：逐字稿為空或輸入檔案不存在 (Edge Case)
```gherkin
  場景 6.1: 傳入不存在的檔案路徑
    假設 使用者執行腳本傳入不存在的路徑 "--audio not_exist.mp3"
    當 系統檢查輸入檔案
    則 系統應印出清晰錯誤提示 "找不到指定的音訊檔案: not_exist.mp3"
    並且 程式以非零狀態碼結束，不發送任何 API 請求

  場景 6.2: 音檔轉寫為空或文字檔案為空
    假設 輸入逐字稿內容為空字串 ""
    當 系統嘗試進行錯別字校正與摘要
    則 系統應直接提示「逐字稿內容為空，無法進行會議記錄生成」
    並且 避免發送浪費資源之 LLM API 請求
```

### 場景 7：會議主題提煉與特殊字元處理 (Edge Case)
```gherkin
  場景: 會議名稱包含作業系統非法字元 (如 \ / : * ? " < > |)
    假設 LLM 產生的標題為 "# 會議名稱：2026/09/16 系統測試: ASR/LLM 優化？"
    當 系統提煉會議名稱作為輸出檔案檔名
    則 系統應自動清理非法字元為 "20260916 系統測試 ASRLLM 優化"
    並且 成功建立檔案，不因非法字元引發 OSError
```

## 前端音檔上傳容錯與保全場景

### 功能 4：音檔上傳階段失敗時的重試與下載保全
```gherkin
功能: 音檔上傳失敗時的重試與音檔下載保全
  作為 一名使用網頁錄音或上傳重要會議錄音的使用者
  我希望 在音檔上傳至後端失敗時，畫面上能提供「重試一次」與「下載音檔」按鈕
  以便於 我能立即重試，並將剛錄製或選取的音檔保存至本地，避免音檔意外遺失

  場景 8.1: 音檔上傳失敗時提供本地音檔下載按鈕
    假設 使用者已完成麥克風錄音或選取音檔，本地存在 File 物件
    當 使用者點擊「開始轉錄會議紀錄」，但後端伺服器斷線或連線逾時導致上傳失敗
    則 頁面應切換至失敗狀態並顯示清楚錯誤提示
    並且 畫面上必須呈現「下載音檔」按鈕
    並且 當使用者點擊「下載音檔」時，瀏覽器應立即將本機音檔 Blob 下載存檔，檔名完整保留

  場景 8.2: 音檔上傳失敗時提供一鍵重試按鈕
    假設 使用者上傳音檔失敗，處於失敗狀態卡片中
    當 使用者確認網路恢復並點擊「重試一次」按鈕
    則 系統應重新進入「上傳中」狀態並使用原本保留之 File 物件再次發送上傳請求
    並且 使用者無需重新錄音或重新開啟檔案選擇器
```
